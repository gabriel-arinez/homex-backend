## Objetivo de la fase

Implementar el núcleo transaccional de venta de HOMEX:

`Proforma APROBADA -> Pedido CONFIRMADO -> VENTA -> stock -> Orden de Trabajo`

y garantizar que la cancelación:

`Pedido CANCELADO -> REVERSA_VENTA -> restitución de stock -> OT CANCELADA`

se ejecute de forma atómica y bajo autoridad de PostgreSQL.

Django coordina el caso de uso, autorización y exposición HTTP, pero no duplica
los efectos comerciales administrados mediante funciones y triggers SQL.

---

## Principio de autoridad

### Aprobación

El servicio `aprobar_proforma()`:

1. inicia una transacción;
2. obtiene la proforma con `SELECT FOR UPDATE`;
3. valida que esté en `ENVIADA`;
4. cambia únicamente su estado a `APROBADA`;
5. PostgreSQL crea el pedido;
6. PostgreSQL genera los movimientos `VENTA`;
7. PostgreSQL actualiza el stock;
8. PostgreSQL crea la orden de trabajo;
9. Django consulta y devuelve el pedido resultante.

Python no crea manualmente Pedido, VENTA, modificación de stock ni OT.

### Cancelación

El servicio `cancelar_pedido()`:

1. inicia una transacción;
2. bloquea el pedido con `SELECT FOR UPDATE`;
3. valida propietario/permisos;
4. valida que no esté previamente cancelado;
5. cambia únicamente el estado a `CANCELADO`;
6. PostgreSQL genera las `REVERSA_VENTA`;
7. PostgreSQL devuelve el stock;
8. PostgreSQL cambia la OT a `CANCELADA`.

Python no genera manualmente movimientos de reversa ni modifica stock.

## Corrección T05

Durante la revisión de F07.3 se identificaron dos debilidades en la validación
original de `REVERSA_VENTA`:

1. era posible intentar registrar directamente una reversa aunque el pedido
   original todavía no estuviera `CANCELADO`;
2. la validación de duplicado mediante `EXISTS` no serializaba dos intentos
   concurrentes sobre la misma VENTA.

Para corregirlo se añadió una migración nueva:

`apps/movimientos_stock/migrations/0002_refuerzo_t05_f073.py`

No se modificaron migraciones históricas ya aplicadas.

La migración incorpora:

- función `fn_reforzar_reversa_venta_t05`;
- trigger `trg_00_reforzar_reversa_venta_t05`.

La protección:

1. actúa únicamente para `REVERSA_VENTA`;
2. exige `movimiento_referencia_id`;
3. comprueba que la referencia corresponda a una `VENTA`;
4. bloquea la VENTA original mediante `FOR UPDATE`;
5. obtiene el pedido original;
6. exige que dicho pedido esté en `CANCELADO`;
7. verifica, después del bloqueo, que no exista otra reversa;
8. permite continuar con las validaciones históricas existentes.

El bloqueo de la VENTA original serializa intentos concurrentes sobre la misma
venta y evita que dos transacciones superen simultáneamente la comprobación
`EXISTS`.

## Manejo de errores comerciales PostgreSQL

Los triggers comerciales utilizan `RAISE EXCEPTION`.

PostgreSQL representa esos errores mediante SQLSTATE `P0001`.

El backend ahora distingue entre:

- errores comerciales esperados provenientes de `RAISE EXCEPTION`, que se
  convierten en `ValidationError` de DRF;
- errores técnicos o de infraestructura, que permanecen como `DatabaseError`
  y no se ocultan como errores de validación del usuario.

Esto permite que situaciones como stock insuficiente produzcan una respuesta
controlada sin debilitar la autoridad de PostgreSQL ni ocultar errores
inesperados.
