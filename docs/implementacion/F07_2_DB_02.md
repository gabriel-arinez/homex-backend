- Rama base: `re-refactor`.

- Objetivo: cotización manual completa sin NLP, con PostgreSQL como autoridad de
  precios, totales, snapshots y congelamiento comercial.

- `apps/core/permissions.py` para el rol runtime `VENDEDOR`; administración

- Migraciones `catalogo.0005`, `proformas.0002` y `proformas.0003`.

## Decisiones aplicadas

- Dos modos de cálculo: `PRECIO_UNITARIO` y `TOTAL_NEGOCIADO`. En el segundo,
  `importe_negociado` es la fuente contractual; tres unidades por Bs 100
  conservan Bs 100 exactos.
- PostgreSQL recalcula `detalle.total`, `subtotal`, `descuento_total` y `total`.
  Una escritura directa de totales de proforma se rechaza.
- Las promociones vigentes BOB se aplican al añadir o editar una línea de
  catálogo; las instantáneas de antes/ahora preservan el precio usado. USD exige
  precio explícito y no aplica conversión.
- Sólo `ENVIADA` constituye demanda pendiente referencial. No modifica stock.
- La primera emisión crea snapshots. Desde `ENVIADA`, cliente y snapshots quedan
  congelados; desde `APROBADA` también se bloquean especificaciones y detalle.
- Las operaciones críticas de edición, especificación y envío bloquean la fila
  de proforma con `SELECT ... FOR UPDATE`.

## Correctivo integral posterior

Se reconfirmaron G01/P29 y T01–T04 mediante PostgreSQL: `TOTAL_NEGOCIADO`
conserva el importe exacto; los totales no admiten adulteración; cliente y
snapshots se congelan desde `ENVIADA`; detalle/especificaciones no se trasladan
ni mutan tras aprobación; edición y envío usan conexiones distintas con
`SELECT FOR UPDATE`.

También se confirmó P22: demanda de proformas `ENVIADA` es sólo referencial y
no modifica `productos.stock`; y P24: promoción vigente usa snapshots
ANTES/AHORA sin un segundo descuento manual. Las APIs exigen autenticación,
rol `VENDEDOR` y aislamiento de objetos ajenos. OpenAPI fue regenerado desde el
contrato real. El job `concurrency-postgresql` ahora ejecuta las pruebas en vez
de limitarse a recolectarlas.


## Cierre de segunda auditoría comercial

Se añadió una regresión específica para impedir que el contexto interno de
recalculo de PostgreSQL permanezca habilitado durante el resto de una
transacción. Después de recalcular una línea, una escritura manual sobre los
totales de proforma continúa siendo rechazada.

Los snapshots `precio_antes_snapshot`/`precio_ahora_snapshot` se reservan
exclusivamente para una promoción real; un producto sin promoción conserva
ambos en `NULL`. También se alineó P22 para que únicamente `ENVIADA` constituya
demanda pendiente referencial: BORRADOR no reserva ni reduce la referencia y
`productos.stock` permanece inalterado.

La validación de emisión ahora se ejecuta al crear o cambiar realmente el estado.
Una edición histórica permitida de una proforma ENVIADA no se bloquea si el
cliente fue desactivado después, mientras cliente y snapshots continúan
congelados.
